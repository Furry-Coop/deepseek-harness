# Agent Note: Session attachment cards and subagent catalog classification

Status: implemented

English | [中文](2026-11-10-session-attachment-cards.zh.md)

## Problem

A business plugin that runs background work for a conversation needs two host capabilities it cannot supply itself. First, it must show a card at a real position in the displayed Session — the start of the Turn whose work it is doing, the event that triggered it, the real `turn/end` that closed that Turn, or the exact Tool call it submitted — while the transcript keeps scrolling, folding, paging, and switching between a fork and its source. Second, it must keep subagents whose work it already presents elsewhere out of the native subagent menu, without losing the native catalog's addresses, lineage, and global activity count.

The existing seams could not express either. `conversation.chat.turnTail` renders only inside a closed Turn's footer and receives the closing reply's sequence, not the Turn's own end; there was no position for a running Turn's start; and a plugin's own card could not name the loaded row it belonged to. The native menu read its rows, total, running count, and empty state directly from the projection, with no place for a business decision.

## Decision

**`ctx.uiConversation.attachments` owns registration; `conversation.chat.attachment` owns rendering.** A registration carries a stable card id, the Session actually on display, a preferred side, and one durable anchor: `turn-start`, `event` with a Session seq, `turn-end`, or `tool-call` with a callId. The id survives a move between anchors; the registry publishes one identity-stable source per Session and removes the card when its registration is disposed. The keyed Slot renders the card with its owner data, so the plugin owns data and lifetime while the host owns position.

**The Chat target resolves the anchor against its loaded timeline, never a stored row index.** `turn-start` and `turn-end` read the public `TimelineSnapshot` Turn boundaries, so paging, folding, and moving are one decision and an ended Turn without a final reply still has its real end. `event` first matches the one loaded root row that declares that durable seq as its new `sourceSeq`. A `step/start` renders no row of its own, so the same anchor next matches a loaded Step whose `StepLocation.start.seq` is that seq and mounts at that Step's first visible row, which the native process group and whole-Turn entry keep reachable while those surfaces are folded. A seq with neither boundary keeps the Turn's start entry. A row's `anchorSeq` is a sortable render position that may be a transient fraction, so it is never compared with a durable seq. `tool-call` matches the loaded Tool Node's own callId and falls back to the Turn entry when the call is unloaded, in another Turn, or duplicated; ordinal adjacency never stands in for the call identity. An unloaded Turn mounts nothing until its page arrives, and a fork has its own Session identity, so it receives no card registered for its source.

**The viewport measures the blank beside the content column and decides between the side blank and the in-Turn position.** Side placement is a measured comparison, not a media breakpoint: the content width is a `clamp()` of the conversation width and a user preference, so CSS cannot compare the two dynamic lengths. The decision reaches CSS as a column attribute and each card as its own host attribute, while a row reports `side` only when every card in it uses the blank. A side card leaves the flow, so appearing, moving, or disappearing never shifts the transcript or writes a scroll position; it shares the native timeline's scroll container and stands in the blank at its resolved position. A side uses the blank for at most one `auto` card: while that side has more than one `auto` card resolved, none of them uses it and all stay in the flow, because a second side card would stand at a nearby anchor without a measured gap and could cover the first. A card registered with `presentation: 'inline'` always stays inside its Turn and does not consume that capacity, so a business can keep its historical entries in place while the active card keeps the side; omission means `auto`, and each card keeps its own host, so the active card still reaches the blank when a historical card resolves to the same side and site. The same mount serves both layouts, so a width change keeps the card, its DOM node, and focus inside it. A side card marks its blank as occupied, so a wide Markdown table in the anchored row stays inside the content column instead of breaking out beneath the card, and a process group that hosts a side card drops its height cap because the capped body is a scroll container that would clip the blank.

**Row-hosted cards name one rendered entry.** A card hosted at a Tool call row or a Step entry targets the exact rendered entry, including the Assistant part, so a Node rendered twice — its reasoning run and its response row — hosts the card once; a Step whose rows live in a process group targets that group's visible entry, which its own disclosure keeps reachable. The viewport supplies the group membership the resolver needs, so the host never guesses a group from row order.

**`ctx.subagentMenu` owns the menu classification.** A classifier receives the actual parent `SessionId` and the complete native entries, returns the entries it already presents elsewhere, and publishes an observable revision that republishes the menu when its evidence changes. That one answer filters the descendant-count menu's rows, total, running count, and empty state; the breadcrumb switcher, addresses, opening a child, and the workspace-wide running indicator keep the complete native catalog. A classifier that throws, answers `undefined`, or returns an unreadable answer is unavailable and contributes nothing, leaving the native rows; disposal restores them, and a failing evidence subscription cannot leave a withdrawn classifier filtering native rows.

## Alternatives considered

**Reuse `conversation.chat.turnTail` and add a Turn-start list slot.** Rejected because `turnTail` belongs to a closed Turn's footer and passes the closing reply's seq, so it cannot mount at a running Turn's start, at an event, or at the exact Tool row; a second independent list would duplicate position resolution and still not scope cards to the displayed Session.

**Let the plugin resolve positions itself from the Chat snapshot.** Rejected because the loaded row set, paging, folding, and the side blank are host-owned, and a plugin reading row positions would duplicate the host's resolution and drift whenever the viewport changes.

**Place side cards with a fixed media or container breakpoint.** Rejected because the content width is adaptive and user-adjustable; a breakpoint would put a card outside the blank or shrink it into an unreadable column at some widths.

**Render a card in both the side blank and the Turn entry and hide one.** Rejected because two mounts duplicate the registration and lose focus and local state on every layout change; one mount with a CSS-only placement keeps card identity.

**Let a throwing classifier blank the menu or fall back to a client-side guess.** Rejected because the host cannot know which native entries a business presents elsewhere; keeping the native rows is the only recoverable behavior.

## Verification

`attachment-registry.client.spec.ts` pins per-Session publication, duplicate ids, malformed anchors, disposal, and card order. `attachments.client.spec.ts` pins every anchor kind against loaded Turns and rows, including a Turn whose loaded rows lack its start, a precise callId, a duplicate callId, an unloaded Turn, registration order at one position, the rule that neither `anchorSeq` nor row adjacency answers a durable event, a `step/start` that resolves to a root row or to its process group, a hidden first row, a Node presented twice, and an unknown seq that keeps the Turn entry. `attachment-layout.client.spec.ts` pins the measured blank decision and the host assignment: a side hosts one `auto` card in the blank, an explicit `inline` card stays in the flow without consuming that capacity, and two `auto` cards on one side all fall back together. `attachment-row.client.spec.ts` pins that one row at one site keeps each card's own host in either registration order. `catalog-classification.client.spec.ts` pins merge order, withdrawal, revision republishing, a throwing classifier, an unreadable answer, an answer that fails halfway through iteration, a failing evidence subscription, and a failing listener. `conversation-ui.client.spec.tsx` pins that the menu rows, total, running count, empty state, native addresses, and nested levels all read one classification. The [issue 18 browser suite](../../../../apps/web/tests/issue-18-host-probe.e2e.ts) drives a real Web scaffold, a controlled model, and Nodes-independent fixture plugins: both sides in the measured blank at wide width, the in-Turn position and preserved focus at narrow width, a Turn that ends without a final reply, an exact durable event anchor and its Turn-entry fallback, a real `step/start` entry with its group disclosure, the exact process call row through its group and Turn entry with the card in the blank, paging, a fork that does not inherit the cards, reader-position and focus stability across a card appearing and moving at both widths, an explicit inline entry staying in the flow while the auto active card takes the blank and its native row seat, an inline history card and an auto active card meeting at one folded Turn entry in both registration orders with one host per card, two auto cards on one side still falling back together, a wide Markdown table staying inside the column under a side card, a long process group's uncapped body with its fold and scroll, and the menu's split, withdrawal, and empty state. The cross-repository real-Nodes case and an externally captured Session are opt-in: they run only when `NODES_REPO` and `ISSUE18_CAPTURE` name those inputs, so a clean checkout runs the suite from its own fixtures.

## Consequences

The host carries a new Session-scoped registry, one keyed Slot, and a measured layout decision, while a business keeps only its own card component and anchor choice. The `seq` reported for a precise Tool row is absent when the row declares no durable source event, so a business must rely on the target callId rather than assume a durable position. An `event` anchor addresses a loaded root row or a loaded Step entry: an event owned by a nested tool row, by no row, or by no Step boundary keeps the Turn entry, and a precise Tool row is addressed through `tool-call` instead. Side placement needs the measured blank, and a side uses it for at most one `auto` card: with more than one, all of them stay in the Turn, which avoids unmeasured occlusion at the cost of the side blank for them, while a card the business marks `presentation: 'inline'` never competes for it. A process group's height cap is dropped while it hosts a side card, so that group is taller than its capped form until the card moves away, and a side card clamps wide-table breakout in its blank while it is present.
