# Agent Note：通过宿主内部受限控制写入提交持久取消记录

Status: implemented

[English](2026-11-08-inbox-cancellation-control-commit.md) | 中文

## 问题

不删除任何待处理输入的取消仍必须留下一个持久事实，冷恢复才能区分用户取消与只是丢失队列的崩溃。该事实属于循环观察到的这次取消，而不属于插件：inbox 拥有待处理输入、turn 信号与清除顺序。当取消发生在另一次追加正在发布期间——例如 hook 在步骤事件上取消——记录由 `session/event` 观察者写入，而日志会拒绝重入追加以保持发布原子。

公开回调队列会让任何消费方在任何发布之后调度任意工作，没有上界，并迫使调用方通过匹配追加错误文本来发现重入。该队列只会有一个生产消费者——循环的取消记录——却会邀请插件调度本应属于各自操作所有者的写入。

## 决定

`Session` 不暴露回调队列。session 包导出 `appendAfterPublication(session, type, data, settled?)`，即宿主内部的控制写入能力。它只接受一条带类型的追加，永不接受调用方提供的回调：存储用参数生成写入，每次发布最多保留一条，拒绝第二次请求并报错。

没有进行中的发布时，记录立即追加，失败直接抛给调用方。发布期间，记录等待在条目的单槽位中，`commit()` 在发布返回之后、延迟 detach 之前排空它，因此记录恰好落在观察到取消的那次发布之后、存储挂接结束之前。延迟追加失败会被记录日志，detach 照常发生，因为它修补的发布已经提交。控制写入触发的嵌套发布不能在打开的排空期间 detach；它排队的写入加入该次排空的尾部。

所有权跟随存储条目。独立 Session 直接追加。已脱离、未进入、仍在公告或公告失败的存储 Session 不会获得延迟写入：立即追加会以存储自身的错误拒绝，因此记录不可能为永远不会发布它的条目排队。可选的 `settled` 完成通知恰好运行一次，并在记录提交或失败之后、或拒绝抛出之前同步运行；因此消费方在同一 tick 就释放所有权，不推迟到微任务。

inbox 记录 `cause`（除 dispose 外的所有原因写 `user`，销毁写 `disposed`）与 `entrySeq`（取消进入时捕获的日志长度），使读取方能区分取消针对的输入与其后追加的输入；带 `keepInbox` 的取消不写任何内容。空队列的用户取消追加一条不删除任何内容的意图 splice，因此 fold 与派生历史不变。`verify-control-write-callers` 门禁放行所属模块、agent-loop inbox、测试与自身，拒绝其他所有生产调用方。

## 考虑过的替代方案

**保留公开回调队列。** 这是该能力最初的形式。它会在任何发布之后运行任意工作，没有上界，并把重入变成字符串匹配（[包规则](../../../../packages/AGENTS.md)：只有一个内部调用方的公开服务方法应改为私有能力）。

**用微任务延迟。** 取消记录必须在存储 detach 会话之前持久化；微任务在同步发布与 detach 路径之后运行，因此紧随发布的销毁会丢失它。

**让插件在发布之后自行补写事实。** 该记录是关于循环自身取消截点的证据，任何较晚的调用方都无法重建；而且插件可能在同一同步栈内销毁会话，早于它能够追加。

**为该事实新增会话事件。** `agent/inbox/spliced` 已经表示待处理输入及其取消，空意图对 fold 是无操作；第二种表示需要自己的读取兼容性，却不增加含义。

**在公告完成之前接受记录。** 记录将不得不在回滚时丢弃，或在公告失败后发布，从而把持久事实变成无主写入。拒绝则把存储的已公告成员规则保留在一处。

## 测试

`packages/core/session/tests/session.spec.ts` 覆盖立即追加、在发布之后 detach 之前落盘的延迟追加、第二次记录被拒绝且两次请求都结算、结算回调抛错、延迟追加失败被容纳且 detach 仍发生，以及未进入、未公告、公告失败或已脱离条目的拒绝。`packages/core/agent-loop/tests/cancel-persistence.spec.ts` 使用真实 AgentLoop 与 JSONL 后端：延迟意图排序在触发事件之后、aborted turn/end 与 detach 之前，从磁盘读回，且对 user、parent、hook 清空记录 `cause: 'user'`，对销毁记录 `cause: 'disposed'`；`keepInbox` 与普通删除保持原有字段；入口截点之后插入的输入继续待处理；意图写入失败后仍记录下一次取消；延迟取消与同栈取消各自记录自己的入口截点；由记录自身观察者触发的取消被限制为一条记录。`packages/core/agent-loop/tests/cancel.spec.ts` 覆盖待处理快照以非 Error 值（含 `undefined`）拒绝时的中止保障及既有取消窗口。`packages/core/agent-loop/tests/initialization-wake.spec.ts` 覆盖空闲空取消写一条意图但不武装任何 turn。`scripts/verify-control-write-callers.spec.ts` 证明门禁拒绝 release 包引用并放行 inbox。

## 后果

session 包新增一个带调用方门禁的导出函数，取代公开的 `Session` 方法；其发布路径只保留一个可选槽位，而不是无界队列。取消记录保持其持久性、顺序与失败行为：在引发取消的观察之后、detach 之前提交，失败被容纳且永不阻断中止。延迟被限制为每次发布一条记录；第二个请求直接失败而不增长队列，每个 inbox 的一个守卫标志限制重入取消。`agent/inbox/spliced` 格式新增两个可选成员，旧读取方会保留并忽略它们，缺失仍是未知历史。`cause: 'user'` 仍表示非 dispose 的取消，而不是已验证的真人点击。
